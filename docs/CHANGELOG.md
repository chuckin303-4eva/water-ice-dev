# Changelog

All notable changes to this project are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/): group entries under Added / Changed / Fixed / Removed / Security, newest release at top.

## [Unreleased]

### Added
- Repository governance structure: `/docs` (ARCHITECTURE, DATABASE, API, ROADMAP, DECISIONS, SECURITY, DEPLOYMENT, USER_GUIDE, CODING_STANDARDS), root README, git branching model (`main`/`develop`/`feature`/`bugfix`/`hotfix`), commit message template, and pre-commit hook scaffold.
- Product direction defined: "Ice & Water Intelligence" location-intelligence SaaS. Stack, core/module architecture, and schema documented in ARCHITECTURE.md and DATABASE.md; recorded in DECISIONS.md as ADR-0002 (Accepted): no PostGIS for v1 (plain lat/lng), cross-tenant resource-pooling confirmed as a core feature, monorepo confirmed.
- Full schema defined (ADR-0003, Accepted): geography (states/counties/cities), locations (full required field set, UUID PK), brands, host_businesses, competitors (site-level), opportunities, photos/documents/reviews (polymorphic attachments), validation_queue, update_log (append-only audit trail), tasks, settings.
- Market Refresh Engine designed (ADR-0004, Accepted): replaceable-provider architecture (OpenStreetMap/Overpass, US Census for v1; USGS/NOAA registered but unbuilt; paid rating/review/photo source deferred until budget exists), refresh -> validation_queue -> human approval -> locations update -> update_log workflow, in-process async execution with no new infrastructure. New refresh_runs table.
- ROADMAP.md restructured into four gated phases (MVP, Validation & Enrichment, Automation & Monetization, Advanced) with every feature ranked Critical/High/Medium/Low, per new PM operating rules.
- Backend project scaffolded (Phase 1, item 1): FastAPI app skeleton, SQLAlchemy models and initial Alembic migration for the Phase-1 subset of the schema (organizations, users, roles, permissions, role_permissions, user_roles, states, counties, cities, brands, host_businesses, locations), Postgres via `infra/docker-compose.yml`, `/health` endpoint, and a starter test suite (`pytest`). No API routes, auth, or business logic yet -- scoped strictly to project skeleton + database per ADR-0002/ADR-0003.
- Added an architecture-conflict gate to CODING_STANDARDS.md: work that would introduce significant tech debt, duplicate existing functionality, or conflict with an accepted ADR must stop, explain why, recommend a better solution, and wait for approval before implementation -- even when directly requested.
- Added `/prompts` (startup, architecture, coding, release, security): short, agent-facing checklists that point to the authoritative docs/ files rather than duplicating them, so there's one source of truth. `startup.md` is the entry point to read before taking any action.
- User authentication (Phase 1, item 2): Argon2 password hashing, JWT access (30 min) + refresh (7 day) tokens, `POST /auth/login`, `POST /auth/refresh`, `GET /auth/me`, and the `get_current_user` dependency. No self-serve registration (deferred to the Admin dashboard item) -- first user created via `backend/scripts/seed_dev_user.py`. Refresh tokens are stateless with no revocation list, an accepted risk recorded in SECURITY.md. Verified end-to-end against a real Postgres instance (seed script, login, protected endpoint, rejection without/with wrong token) plus 16 automated tests.
- Location management (Phase 1, item 3, ADR-0006, Accepted): `POST/GET/PUT/DELETE /locations` built as prospecting -- create by pin or address (Nominatim geocoding fills in whichever is missing, plus resolves state/county/city), 17 new prospect fields (property owner/management/contacts, expected unit size, power/water/sewer connection description + company, pricing estimate). `location_call_notes` (append-only call log with optional `follow_up_at`) plus `GET .../calendar-link` generating Google Calendar/Outlook "add event" deep links -- no OAuth, works with no frontend. `update_log` (designed in ADR-0003, never built until now) implemented and wired into every location create/update/archive. Power/water utility auto-lookup designed but deferred (real free federal data sources confirmed: EIA, OpenEI URDB, EPA); property ownership and sewer availability confirmed to have no free source and stay manual indefinitely. New dependency: httpx (geocoding HTTP client, already used in tests). 36 tests total (20 new), all passing, verified end-to-end against live Postgres with real Nominatim calls -- including a real-world edge case (Denver's consolidated city-county has no separate "county" in OSM data) correctly falling back rather than crashing.
- Interactive map, first frontend (Phase 1, item 4, ADR-0007, Accepted): new `frontend/` app (React 19 + TypeScript + Vite + Tailwind v4 + Leaflet/`react-leaflet` + `leaflet.markercluster`). Login (JWT stored in `localStorage`, flagged as an XSS trade-off to revisit before public exposure), a clustered map with status-colored markers (prospect/active/archived), add-prospect by clicking the map or typing an address (pin/address only per the minimal-scope decision -- everything else filled in afterward via the detail panel), a detail panel showing key prospect fields plus call notes and an authenticated "add to calendar" button (Google/Outlook). Tile provider is raw OpenStreetMap for now via env var, explicitly dev-only -- OSM's usage policy prohibits production use of the public tile server; a free-tier commercial provider (MapTiler/Stadia) is the swap before real users, tracked in ADR-0007. Backend: added `CORSMiddleware` with an env-driven `cors_origins` setting (default `http://localhost:5173`), since the backend previously had no frontend to allow. Verified: `tsc -b` + `vite build` clean with no errors, and a full manual browser + API pass against the real backend -- login, map load, add-prospect by address (real Nominatim geocode), call note with follow-up, and calendar-link generation all confirmed working end-to-end.
- Competitor tracking (Phase 1, item 5, ADR-0008, Accepted): new `competitors` table + `POST/GET/PUT/DELETE /competitors` (designed in ADR-0003, never built until now; field set widened with `is_inside`, `machine_size`, `ice_price`, `water_price`, `price_notes`). Map: competitors render as their own orange **square**-icon cluster layer, visually distinct from location pins by both color and shape (accessibility -- color alone isn't a reliable cue for color-vision-deficient users); a click-to-view/edit panel shows address, inside/outside, brand, size, ice/water, and price. Location pins now read `opportunity_score` (newly exposed on `LocationSummary`) to color prospects green once scored well, yellow otherwise -- forward-compatible with Basic Scoring (Phase 1, item 6), which doesn't exist yet, so every current prospect is yellow. Researched (not assumed) whether Denver-area competitor data could be auto-populated: confirmed no free, scrapeable source exists for specific ice/water vending machine addresses (major brands gate their locators behind mobile apps or interactive maps; OSM has essentially no coverage for this niche) -- the map is not pre-populated with fabricated data; real entries are added by hand via the map, same honesty policy as ADR-0006's utility-lookup deferrals. A Maps-scraping browser extension was explicitly considered and rejected (ToS violation risk, photo-copyright exposure) -- see ADR-0008. 8 new backend tests, all passing; verified end-to-end in a real browser against the real backend (create by address, click to view, edit, delete).
- Competitor contact/follow-up fields + compact entry form (ADR-0008 addendum): after trying the paste-matching UI once, replaced it with a compact manual-entry form (small fields: location name, brand with autocomplete suggestions for Twice the Ice/Kooler Ice/Watermill Express, address or click-to-place-pin, website, phone, contact name, email, and a follow-up date/time) -- `parseMapsListing.ts` removed as dead code. New `Competitor` fields: `brand`, `website`, `phone`, `contact_name`, `contact_email`, `follow_up_at`; new `GET /competitors/{id}/calendar-link` (reuses the existing `calendar_link_service` unchanged) generating the same Google Calendar/Outlook "add event" deep links as location call notes, surfaced both right after creating a competitor (when a follow-up was set) and later from the detail panel. 5 new backend tests (47 total), all passing; verified end-to-end in a real browser (create with all fields, calendar-link generation, detail panel view/edit).
- Basic scoring (Phase 1, item 6, ADR-0009, Accepted): new `app/services/scoring_service.py` computes `competition_score` for real (app-level haversine distance to nearby `competitors`, no PostGIS per ADR-0002 -- capped, distance-weighted, 0 with no nearby competitors is a real answer not a missing one) and `opportunity_score` as a composite of that plus two newly-exposed manual 1-10 ratings, `visibility_rating` and `traffic_score` (both existed as unused columns with no defined scale since Phase 1). `opportunity_score` is `null` until both ratings are set -- no default-guessing from missing inputs. `population`/`median_income`/`growth_rate` deliberately excluded from the formula (no free demographic source wired yet, Phase 3). Recalculates automatically on location create/update; new `POST /locations/{id}/recalculate-score` covers the case where nearby competitor data changed instead. Frontend: `LocationDetailPanel` gets a Score section (opportunity/competition/visibility/traffic display, a "Rate this site" form, and a "Recalculate" button), wired to refresh the map's marker list on change so a pin's color updates immediately, not just on next reload (a related bug found and fixed in the same pass). 12 new backend tests (59 total), all passing; verified end-to-end in a real browser -- rating a site to 10/10 visibility/traffic produced `opportunity_score: 100`, `confidence_score: 100`, and the pin turned green live on the map with no reload.
- Filters (Phase 1, item 7, ADR-0010, Accepted): server-side query-param filtering on `GET /locations` (`statuses` repeatable, `serves_ice`/`serves_water` opt-in, `min_opportunity_score`) and `GET /competitors` (`serves_ice`/`serves_water`, `brand` case-insensitive partial match) -- filtered in the SQL query, not client-side after fetching everything, per the schema's 100k-location design target. `status_filter` (single-value) replaced by `statuses` (repeatable multi-value); no external consumers exist yet, so this is a clean rename. Ice/water checkboxes are opt-in narrowing (OR across whichever are checked), not exclusion -- both default to `false` on a brand-new, unconfigured prospect/competitor, so an exclude-based filter would make every fresh entry vanish the moment the panel was touched. New compact `FilterPanel` on the map (bottom-left): status checkboxes, ice/water requirement checkboxes, a minimum-opportunity-score input, and a client-side show/hide toggle for the competitor layer (pure visibility, no backend round-trip). 5 new backend tests (64 total), all passing; verified end-to-end in a real browser -- status filter, combined status+score filter, and the competitor toggle all confirmed via network log and marker-color inspection.
- Import CSV (Phase 1, item 8, ADR-0011, Accepted): new `POST /locations/import` (multipart file upload) bulk-creates locations from a CSV, minimal column set (`address` or `latitude`+`longitude`, `serves_ice`, `serves_water`, `notes`) matching the same "minimal add, fill in the rest later" split used everywhere else a prospect gets created. Rows reuse `location_service.create_location` one at a time with a ~1.1s delay between them to respect Nominatim's real ~1 req/sec usage policy at bulk volume (never an issue for one-at-a-time human creation); a 100-row cap keeps a single request's duration bounded, rejected upfront (422) rather than silently truncated. Partial success: a bad row is recorded as a per-row error (`{row, message}`) without blocking the rest of the file, and already-created rows aren't rolled back if a later row fails. New `ImportCsvControl` on the map (bottom, next to Filters) shows upload progress and a created/error summary. New runtime dependency: `python-multipart` (required by FastAPI's file-upload support). 6 new backend tests (70 total), all passing; verified against the live running server via both a real curl multipart upload and the actual browser file-input flow -- confirmed `{"total_rows":2,"created":2,"errors":[]}` and the UI showing "Created 2 of 2 rows."
- Admin dashboard (Phase 1, item 9, ADR-0012, Accepted): `POST /auth/register` creates a brand-new organization plus its first (admin) user and logs them in immediately -- fulfills a promise both `docs/API.md` and `backend/scripts/seed_dev_user.py`'s own docstring had been making since Phase 1 item 2 ("until the Admin dashboard exists..."). Two system-wide roles, `"admin"`/`"member"` (get-or-created lazily, same pattern as geography rows), enforced via a new `require_admin` dependency -- the `permissions`/`role_permissions` tables stay deliberately unused (no fine-grained capability needs gating yet). New `GET/POST /organizations/users` and `PUT /organizations/users/{id}` (admin-only creation/updates; any authenticated org member can list their own roster). Creating a teammate sets their password directly, shown once -- no email service exists to send an invite through, and that's stated plainly rather than faked. Org-lockout prevention is a single rule -- the endpoint always rejects modifying your own account -- which alone makes 0 active admins unreachable given every org starts with exactly one; a separate "count active admins" guard was built, found to be provably dead for that purpose (and a source of a false-positive bug) via a dedicated verification pass, and removed rather than kept as decoration. Frontend: first real use of `react-router-dom` (installed since ADR-0007 but never wired in) -- proper `/login`, `/register`, `/`, `/admin` routes, with `/admin` gated both client-side (redirect) and server-side (403). New `RegisterPage` and `AdminDashboardPage` ("Team" nav link, admin-only). 24 new backend tests (85 total), all passing; verified end-to-end in a real browser -- registration, teammate creation with the shown-once password, live role change, deactivation blocking login, and both the client-side redirect and server-side 403 for a non-admin hitting `/admin`.

### Changed
- Replaced the pre-work approval gate with an Autonomous Execution Policy (ADR-0005, Accepted): default is now autonomous execution through a full milestone, pausing only for a destructive migration/irreversible data op, a backward-compatibility break, missing credentials/licenses/resources, a legal/compliance/platform-policy limit, or a genuine fork between equally-valid business strategies. The architecture-conflict gate and the PM pre-work status report both changed accordingly -- they now explain/record/report and proceed, rather than stop and wait. See CODING_STANDARDS.md and DECISIONS.md ADR-0005.

### Fixed
- `AddProspectControl`/`AddCompetitorControl`/detail panels no longer leak clicks to the underlying map. These overlay controls are rendered as children of react-leaflet's `<MapContainer>`, making them real DOM descendants of Leaflet's map container; clicking any button or input inside them also bubbled up and fired the map's own "place a pin" click handler, silently creating an extra prospect/competitor at whatever screen coordinate the button occupied. Fixed with a small `useStopMapClickPropagation` hook applying the same `L.DomEvent.disableClickPropagation` technique Leaflet's own zoom controls use internally. Found while building the competitor "Add" flow; verified fixed via real browser testing (single `POST` per submission, confirmed via network log).
- `infra/docker-compose.yml` now sets an explicit Compose project `name: water-ice-dev`. Without it, Compose derived the project name from the compose file's parent directory ("infra"), which collided with another local project that also stores its compose file at `infra/docker-compose.yml` -- starting that project's stack recreated this project's Postgres container under different settings. No data was lost (confirmed before and after), but the container/volume were recreated as `water-ice-dev-postgres-1` / `water-ice-dev_postgres_data`; the dev seed user was recreated. If you have a local `.env` or scripts referencing the old `infra-postgres-1` container name, update them.
- `backend/tests/conftest.py`'s in-memory SQLite test engine now uses `poolclass=StaticPool`. Without it, a commit followed by a request handled in FastAPI's threadpool can check out a fresh, schema-less `:memory:` connection instead of reusing the one the schema was created on -- latent in this project (no test yet happened to hit the exact commit-then-query-again pattern that triggers it), found and fixed while building the same test pattern on another project.
